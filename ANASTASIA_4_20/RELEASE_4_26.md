# Анастасия 4.26 RC1 — отчёт и эксплуатация

Дата: 16 ноября 2026. Основа: локальная версия 4.25 SALES, выбранная пользователем.
Указанный исходный RAR недоступен; побайтовое сравнение с ним не выполнялось.
Статус: **кандидат релиза, НЕ production-ready**. Внешние критические проверки и
добровольная оценка диалогов не выполнены. Рабочие ключи, базы и сессии не изменялись.

## Что изменено

- doctor.py: отсутствующие/неверные обязательные настройки и зависимости дают код 1.
  Проверяются положительные ID, два разных директора, формат API hash, имя сессии,
  непустые ключ и модель, логические переключатели. Это проверка синтаксиса, а не
  действительности учётных данных у провайдера.
- run_tests.py: удаление унаследованных настроек приложения, ключей и OPENAI_BASE_URL;
  отключение dotenv и сторонних pytest plugins; отдельная временная папка pytest.
  Исходные данные не копируются. Моки блокируют внешние socket-подключения;
  loopback Windows разрешён для механизма asyncio.
- check_readiness.cmd: сохранение кода возврата doctor.py после pause.
- release_gate.py: отсутствующее свидетельство, непроверенная интеграция, любое
  критическое нарушение или оценка ниже 4 блокируют выпуск. Это проверка введённых
  свидетельств, а не независимый доказатель корректности.
- tests/test_release426.py: 35 новых тестов конфигурации, изоляции и критериев выпуска.
- tests/release_matrix.json: 100 дополнительных сценариев A–J, по 10 на категорию.
  Исходный корпус из 62 диалогов сохранён; новые 100 сценариев имеют статус not_run.
- .env.example: актуальная версия и исправленная ссылка на документацию.
- start.cmd: актуальная версия в сообщении запуска.
- Добавлены инвентаризация окружения, проверенные версии зависимостей, инструкции,
  шаблон свидетельств и машинные результаты. Полный список: CHANGED_FILES_4_26.txt.

## Ограничения и блокеры

Не проверены живые Telegram login/reconnect/RPC, настоящий OpenAI ключ и качество
ответов выбранной модели, серверная семантика AlfaCRM, обновление реальной установки,
чистая Windows без Python/интернета, установка зависимостей с нуля и добровольные
разговоры. Полный запуск start.cmd подключает Telegram и здесь не выполнялся.
Изолированные тесты выполнялись на Windows в уже установленном окружении.
Наличие теста миграции не доказывает совместимость любой клиентской базы.

При неопределённом исходе доставки действует предотвращение автоматического повтора:
возможна пропущенная доставка, требующая ручной сверки. Гарантировать exactly-once
между SQLite и внешней CRM/Telegram нельзя. Контроль дублей проверен моками;
параллельные внешние системы могут создать дубликат независимо от этого приложения.
Prompt injection проверяется на границах ролей и действий, но устойчивость живой модели
к любым формулировкам не доказана. LOG.exception в старых ветках может сохранять
детали SDK: журналы считать конфиденциальными, не публиковать без очистки.
Полный аудит зависимостей на CVE не выполнялся. Подтверждения production-ready нет.

## Установка

1. Распаковать архив в отдельную локальную папку. Нужен Python 3.11+.
2. `py -3 -m venv .venv`, затем `.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`.
   requirements.txt содержит диапазоны; requirements-tested.txt — снимок проверенного
   окружения, пригодный для воспроизведения через `pip install -r requirements-tested.txt`.
   Wheel-пакетов в архиве нет; установка без интернета требует заранее подготовленного wheelhouse.
3. Скопировать `.env.example` в `.env`, заполнить собственные настройки. Оставить
   SAFE_TEST_MODE=true, CRM_ENABLED=false и исходящие функции выключенными.
4. `.venv\Scripts\python.exe run_tests.py`; `.venv\Scripts\python.exe doctor.py`.
   Пустой шаблон намеренно не проходит doctor. Ключи на экран не выводятся.
5. `.venv\Scripts\python.exe main.py listen` — только после настройки своего тестового
   аккаунта. SAFE_TEST_MODE отключает клиентские эффекты, но listen всё ещё использует
   Telegram; команды тестирования могут обращаться к OpenAI и расходовать токены.
6. Существующие .cmd сохранены. Они выбирают `py -3`, если доступен, иначе `python`;
   установка через install_dependencies.cmd и запуск через start.cmd используют этот
   же механизм. Для строгой изоляции использовать явный путь к .venv, как выше.

## Конфигурация

Полный перечень прямых обращений к окружению с местом и значением по умолчанию:
CONFIG_ENV_INVENTORY.json; динамические имена ALFACRM_{ALEX,YARO}_* сохранены как выражения.
Обязательны Telegram API ID/hash и собственная авторизация, OpenAI key для LLM;
два разных положительных numeric ID нужны для административного управления.
TG_PHONE применяется при авторизации; существующая сессия находится в
data/sessions/<TG_SESSION_NAME>.session. Имя по умолчанию anastasia_own_login.
Не менять имя при обновлении без намерения создать новую сессию.
Модель по умолчанию gpt-5-mini; глобальная конфигурация панели имеет приоритет
над OPENAI_MODEL. Доступность модели проверяется отдельно на тестовом ключе.
Стиль: клиент > группа > глобальные настройки; безопасность, согласия и достоверные
факты выше стиля; индивидуальная настройка не отменяет глобальный запрет отправки.
Для AlfaCRM нужны HTTPS URL, email, key и numeric branch каждого используемого города.
CRM_ENABLED включает интеграцию, но не заменяет согласия клиента.
Новые обязательные переменные не добавлены. Устаревшие поля шаблона сохранены для совместимости.

## Обновление, резервная копия и откат

1. Остановить main.py и панель. Убедиться, что процессы закрыты; не копировать живую SQLite
   обычным копированием. Сохранить всю старую папку в закрытом месте, включая .env,
   data/, SQLite и при наличии -wal/-shm, сессии и пользовательские JSON-файлы.
2. Развернуть новый код отдельно. Перенести в него копии .env и всего data/, сохранить
   свои knowledge.json, approved_groups.json и локальные изменения после сравнения.
   Не переносить эти данные в публичный архив. Не заменять .env шаблоном.
3. Для приёмки использовать дополнительную копию, тестовые аккаунты и согласованные
   контакты. Сначала run_tests.py, doctor.py, затем проверка миграций на копиях баз,
   целостности SQLite, истории, согласий, запретов и статистики. Запуск модулей может
   создать/обновить SQLite; исходная резервная копия должна оставаться неизменной.
4. До выполнения критических проверок не переключать production на этот RC.
5. Откат: остановить новый процесс, отдельно сохранить его данные для разбора,
   восстановить весь согласованный комплект старого кода, окружения и данных из backup.
   Не запускать старый код поверх базы после новых миграций без отдельной проверки.
   После внешних отправок сначала сверить ledger и CRM: возврат старой базы может
   забыть отправки и привести к повтору. Автоматический повтор после отката запрещён
   до сверки оператором.

## Выпуск

Заполнить release_evidence.json фактическими результатами по инструкции VOLUNTEER_QA.md.
`python release_gate.py release_evidence.json` должен вернуть 0 только после закрытия
всех блокеров. Сейчас ожидается код 1. Критическое нарушение нельзя компенсировать
средней оценкой. Проверка критерия выпуска не отключает приложение автоматически:
решение о развёртывании остаётся отдельным процессом.
